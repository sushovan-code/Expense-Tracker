# Roadmap: family groups and follow-up features

Status: **proposed** (2026-11-08). Each numbered slice is one branch and one PR, built and tested end to end before the next one starts. Tick a slice when its PR merges.

## Guardrails (apply to every slice)

- **Look and feel stays the same.** Existing screens, flows, navigation, themes and colours are unchanged. New screens and controls are built only from the existing `shared/ui` components, the `app/styles/tokens.css` tokens and the current layout. No new colours, fonts or theme behaviour.
- **RBAC and JWT bearer authentication stay the same.** Login, refresh, logout, the token contents, `IUserAccessProvider`, `Permissions`/`AppRoles`, `AccessPolicy`, API keys and the admin screens aren't modified. Family access is a **separate, additional check** that runs after the existing authorisation:
  - The app permission decides **whether** you may add, view or edit expenses at all; the existing RBAC does this.
  - The family role decides **which family's data** you see and **what you may do inside it**. This layer is new and lives in its own code.
  - App admins (SuperAdmin and Admin) keep managing users and roles app-wide. They see only their own family's expenses, like everyone else.
- **Persistence stays behind the ports**, so moving to MongoDB Atlas later only means new adapters (see slice 2 and ADR 0001).
- **Asking first.** Every new NuGet or npm package and every public-contract change is listed in its slice and needs your approval before that slice starts.

## 1. `chore/sqlite`: move the database from SQL Server to SQLite
This slice replaces adoption-plan slice 2 (Testcontainers is no longer needed).

- [ ] Swap the provider package `Microsoft.EntityFrameworkCore.SqlServer` for `Microsoft.EntityFrameworkCore.Sqlite`, and remove `OpenTelemetry.Instrumentation.SqlClient`. *New package; needs approval.*
- [ ] Connection string `Data Source=App_Data/expense-tracker.{env}.db`. `*.db` is git-ignored. No database prerequisite or container is needed, so it runs on Windows, macOS and Linux CI.
- [ ] Fix what SQLite doesn't support (from the [EF Core SQLite limitations](https://learn.microsoft.com/ef/core/providers/sqlite/limitations)):
  - [ ] **`DateTimeOffset` can't be compared or sorted in SQL.** Add a model-wide value converter that stores UTC ticks (`long`), so these keep running in SQL: `AuthService.cs:72` (delete expired refresh tokens), `ApiKeyService.cs:47` (count active keys) and `UserAdminService.cs:50-53` (sort by created or last login). This is storage only; the auth logic doesn't change.
  - [ ] **No schemas.** Drop the `auth` schema from `IdentityConfiguration.cs`. The table names already don't clash.
  - [ ] **Search would become case-sensitive** (`Contains` turns into `instr()`). Use a `NOCASE` collation on `Description`, `Notes` and `Category.Name`, so search and duplicate-name checks behave as they do today.
  - [ ] `decimal` needs no change: EF translates comparisons and aggregates for it on SQLite.
- [ ] **Reset the migrations.** Delete the 3 SQL Server migrations and generate one SQLite `InitialCreate`. The data is synthetic and the dev database is recreated on first run.
- [ ] Integration tests get a fresh SQLite file per test class, deleted afterwards. No Docker. This also fixes the shared-database gap in the adoption plan.
- [ ] Update the README "Run it locally" section (remove the LocalDB prerequisite), CI and the diagrams.
- [ ] Write **ADR 0001, "SQLite now, MongoDB Atlas later"**. The MongoDB EF Core provider has no migrations, no joins across collections and no ASP.NET Identity EF store support. So for the Mongo move:
  - The identity store will need its own adapter.
  - Read queries stay port-shaped (`IExpenseQueries` …).
  - New tables use Guid IDs generated by the app.

## 2. `feature/<n>-family-groups` (main feature)

**Data**
- [ ] `Family` (Id Guid, Name, CreatedAt).
- [ ] `FamilyMember` (FamilyId, UserId **unique**, Role: Owner | Member | Viewer, JoinedAt). One family per user.
- [ ] `FamilyInvite` (Id, FamilyId, Role, TokenHash, CreatedByUserId, ExpiresAt = created + **48 h**, AcceptedAt?, RevokedAt?). The token is stored hashed and works once.
- [ ] `Expense` gains `FamilyId`, `CreatedByUserId` and `IsPrivate`.
- [ ] `Category` gains `FamilyId`; names are unique per family. The global `HasData` category seed is replaced by a default set copied into each new family.

**Rules** (`FamilyPolicy`, pure functions with unit tests, alongside and independent of `AccessPolicy`)
- [ ] **Owner:** manages members, invites and roles; manages categories and budgets; edits or deletes any shared expense.
- [ ] **Member:** adds expenses; edits or deletes their own.
- [ ] **Viewer:** read only.
- [ ] A family always keeps at least one Owner (the last Owner can't leave or be demoted).
- [ ] **Private** expenses are visible only to their creator, the Owner included.

**Isolation** (defence in depth)
- [ ] New Application ports: `ICurrentUser` (the user ID from the existing claims) and `ICurrentFamily` (FamilyId and family role). `ICurrentFamily` is resolved by a new family-membership lookup with its own HybridCache entry, invalidated when membership changes; it never touches `IUserAccessProvider`.
- [ ] EF Core **named global query filters** on `Expense` and `Category`:
  - `"Family"`: `FamilyId == currentFamilyId`. A user without a family matches nothing.
  - `"Private"`: `!IsPrivate || CreatedByUserId == currentUserId`.
  - `ExecuteDelete`, `Count` and `Sum` all honour them.
- [ ] A SaveChanges interceptor stamps `FamilyId` and `CreatedByUserId` on inserts, and rejects updates or deletes of rows from another family.
- [ ] Another family's IDs return **404**, not 403, so their existence isn't revealed.
- [ ] `IgnoreQueryFilters()` is allowed only in named background or admin code paths, and an architecture test enforces this.
- [ ] SignalR events go to a `family:{id}` group, and private-expense events only to their creator. This uses SignalR groups on the existing hub; the connection's authentication is unchanged.

**Use cases and endpoints** (`/api/families/...`; they add to the public API without changing existing routes)
- [ ] Create my family (the creator becomes Owner, and the default categories are seeded), get my family, rename it.
- [ ] Owner **adds a member directly**: creates the account through the existing identity store with the default app role `User`, then adds the membership. App roles are never changed by family actions.
- [ ] Owner **creates an invite link** (shown once, for you to share yourself) and revokes invites.
- [ ] **Accept an invite.** This is an anonymous, rate-limited endpoint: it creates the account and joins the family. A signed-in user who has no family can also accept. After that, the person signs in through the existing login.
- [ ] Change a member's role, remove a member, leave the family.
- [ ] Expense list, summary and export gain a member filter: **Everyone** (default) or one member.

**Web** (existing components only)
- [ ] A **Family** item in the existing left navigation, opening a members table, an "Add member" modal and an invite modal with a copy button (reusing the Grid, Modal, Field and toast components).
- [ ] An **Accept invite** page that reuses the existing login page layout.
- [ ] Expense form: a **Private** checkbox (the existing Checkbox). Expense filters: a **Member** select next to the current ones.
- [ ] A signed-in user without a family sees the existing empty-state component with a **Create family** action.

**Seed (Development)**
- [ ] Two demo families. The **Sharma family** has user@ as Owner, admin@ as Member and reader@ as Viewer; a second family with its own users makes the isolation visible. The README test-users table is updated.

**Tests**
- [ ] Domain: Family, FamilyMember and FamilyInvite rules, including invite expiry with `FakeTimeProvider` (47 h 59 m valid, 48 h expired) and single use.
- [ ] `FamilyPolicy` unit tests for every role-and-action combination.
- [ ] Use cases tested with NSubstitute fakes.
- [ ] **Isolation integration tests**: with two families A and B, B gets 404 or empty results for A's expenses and categories on list, get, update, delete, bulk delete, export, summary and budgets. A family member never sees another member's private expense, the Owner included. Family B's hub connection never receives family A's events.
- [ ] Architecture test: every entity with a `FamilyId` has the `"Family"` query filter.
- [ ] Unauthenticated and unauthorised tests for every new endpoint.
- [ ] Frontend: the family page ViewModel, the member filter, the private checkbox, the accept-invite page.

## 3. `feature/<n>-login-qr`: QR code on the login page
- [ ] A small **QR icon button** on the login page (existing icon style) opens the existing Modal with a QR code of the site's URL. Scanning it on a phone opens the same website at the login page; the person signs in with the normal flow. This is not a device-login handshake, so authentication doesn't change.
- [ ] URL source: `VITE_PUBLIC_URL` when set, otherwise `window.location.origin`. On a dev machine `localhost` isn't reachable from a phone, so the README explains running Vite with `--host` and setting `VITE_PUBLIC_URL=http://<LAN-IP>:5010`, plus the matching CORS origin.
- [ ] Rendered as SVG in token colours, so it switches with the light and dark themes.
- [ ] Tests: the button opens the modal, and the code encodes the configured URL.
- [ ] *Needs approval for an npm package:* `qrcode` (MIT).

## 4. Follow-up features (in your order; each gets a short plan before it starts)
- [ ] **4.1 Monthly budgets, total and per category.**
  - Progress bars in the existing budgets card style.
  - Alerts at **75%, 90% and 100%** as SignalR toasts through the existing toast system.
  - A `BudgetAlertLog` table with a unique key (FamilyId, CategoryId or total, Year, Month, Threshold), so each alert fires once a month.
  - This replaces today's single "crossed 100%" alert.
- [ ] **4.2 Income entries and savings goals.**
  - Simple income entries.
  - Goals with a target amount and date.
  - Progress = income − expenses per month.
- [ ] **4.3 Recurring expenses** (rent, EMIs, school fees, subscriptions).
  - A hosted `BackgroundService` that uses `TimeProvider`, so no scheduler package is needed.
  - Creation is idempotent per (rule, month).
  - A reminder toast 3 days before each one is due.
- [ ] **4.4 Payment method** (UPI, card, cash) **and paid by** (a family member), with a breakdown by each on the dashboard.
- [ ] **4.5 Trends.** The dashboard already has a 6-month bar chart and a month total compared with last month. This slice adds the **per-category** comparison of this month with last month, next to the existing donut chart, using the existing `recharts` library.
- [ ] **4.6 Search and filters** by amount range (the date, category and member filters already exist by this point), plus **Xlsx** export alongside CSV. *Xlsx needs a package (for example ClosedXML, MIT), which needs approval.*
- [ ] **4.7 Receipt photo.**
  - An `IFileStorage` port with a local-disk adapter (Azurite or Blob storage later).
  - Checks the image's file signature and size.
  - Uses `<input type="file" accept="image/*" capture="environment">`, which opens the camera on Android.
- [ ] **4.8 Activity log and soft delete.**
  - Records who added, edited or deleted what, and when.
  - Deletes become soft deletes, with a **10-second undo** toast. The undo toast exists today, but it re-creates the expense; a soft delete restores the original row, with its ID and history.
  - A `"NotDeleted"` named query filter hides deleted rows.
- [ ] **4.9 Custom categories per family**, each with an icon (from the existing icon set) and a colour (from the existing category colour palette).
- [ ] **4.10 Monthly summary** on the 1st: an in-app report with the total, top categories and whether each budget was hit or missed. Generated by the background service.
